# 开发与协作规范

## 1. Git 工作流

- `main`：始终保持可演示，合并前必须通过检查。
- `feature/<module>-<short-name>`：功能分支，例如 `feature/story-node-api`。
- `fix/<short-name>`：缺陷修复。
- 一次提交只处理一个逻辑目标，提交信息示例：`feat(project): add member role update`。
- 禁止提交 `.env`、密钥、数据库数据目录、`node_modules`、`target`。

推荐 Pull Request 检查：需求/Issue 链接、截图或接口示例、测试结果、数据库是否变化、文档是否更新。

## 2. 命名约定

| 对象 | 约定 | 示例 |
|---|---|---|
| Java 类 | PascalCase | `StoryNodeServiceImpl` |
| Java 方法/变量 | camelCase | `listAccessibleNodes` |
| REST 路径 | 小写复数、短横线 | `/api/projects/{projectId}/story-nodes` |
| 数据库表/字段 | snake_case | `story_choice.source_node_id` |
| Vue 组件 | PascalCase | `NodeEditorPanel.vue` |
| TS 函数/变量 | camelCase | `createStoryNode` |
| 业务错误码 | UPPER_SNAKE_CASE | `PROJECT_ACCESS_DENIED` |

## 3. API 开发顺序

1. 在 `docs/05-接口与错误约定.md` 确认路径和字段。
2. 建 DTO 并添加 Jakarta Validation。
3. 在 Service 接口定义业务边界。
4. Service 实现权限、事务和异常。
5. Mapper 只处理数据访问。
6. Controller 只做协议适配。
7. 增加成功、越权、非法状态和不存在资源测试。
8. 前端接入并补空态、加载态、错误态。

## 4. 数据库变更规则

- 数据库统一使用 MySQL 8，以 `database/*.sql` 作为可交付、可复现的结构与数据来源；Navicat 仅作为连接、执行 SQL 和管理数据的客户端。
- 开发者 B 负责 E-R 设计、`schema.sql`、迁移脚本、演示数据和 Navicat 执行验证；开发者 A 负责 Mapper、事务及 SQL 与后端实体/DTO 的一致性复核。
- 课程初期直接维护 `schema.sql`；进入多人并行阶段后新增 `database/migrations/Vxxx__name.sql`，不修改已执行迁移。
- 新增项目子表必须包含 `project_id` 和索引。
- 外键删除行为必须显式决定：级联、限制或置空。
- 不使用数据库枚举类型，以 VARCHAR + Java 白名单便于演进。
- JSON 仅用于状态快照和无法固定列的审计内容，不替代正常关系设计。

## 5. 权限检查模板

所有项目子资源写操作遵循：

```text
取得 currentUserId
→ 查询 projectId 对应成员关系
→ 验证成员角色是否允许当前动作
→ 查询子资源，同时校验 resource.projectId == projectId
→ 验证业务状态
→ 在事务中写入
```

不得先按 `nodeId` 更新，再依赖前端保证它属于当前项目。

## 6. 测试最低要求

- Service：规则、权限、状态流转必须单测。
- Mapper：复杂查询使用 MySQL 测试库做集成测试。
- Controller：至少覆盖 400、401、403、404、409。
- 前端：`npm run typecheck`、`npm run build` 必须通过。
- 每个 P0 用例都应有一条手工验收脚本。

## 7. 前后端与数据库协作的冲突控制

- B 负责数据库字段和 SQL 初稿，A 负责确认实体映射、事务和后端 DTO，双方在实现前共同确认是否满足页面状态与业务约束。
- B 可以先使用固定 JSON mock，但字段名以已评审契约为准；数据库字段变化必须同步通知 A。
- `schema.sql` 和迁移脚本原则上只由 B 修改；A 如需变更，先提出字段需求并由 B 落库，避免并行冲突。
- 发生契约变化时，提交中同时更新前端类型、接口文档和测试。
