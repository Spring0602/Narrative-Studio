实际验证内容包括：

## 3. 解决的主要问题

### 3.1 历史列表无法在一张截图中完整显示

历史记录弹窗使用内部滚动区域，一张截图无法同时显示最近 5 份记录。最终采用顶部和底部两张连续截图，分别证明 V6 至 V3 以及底部 V2 的存在，同时确认 V1 已被淘汰。

### 3.2 刷新后编辑表单关闭

未提交表单在刷新后不会直接覆盖正式数据，而是在顶部显示“本机未提交草稿”入口。通过打开草稿预览并点击“恢复到编辑表单”，成功恢复世界观和角色档案内容。

### 3.3 多窗口可能覆盖自动草稿

使用两个浏览器窗口持有不同修订号，等待窗口 A 完成自动保存后，再返回窗口 B。系统能够检测旧修订冲突、暂停自动保存并提示先检查恢复记录，避免静默覆盖。

### 3.4 后端断开时页面加载失败

主动停止后端并刷新页面，确认前端不会白屏，而是显示“项目加载失败”和“重新加载”入口；后端恢复后页面可以重新正常加载。

### 3.5 Workbench 多结果标签不易识别

三个核验脚本会生成多个 Result Grid。通过逐条执行关键只读查询、核对预期行数和异常计数，并为每项结果单独命名截图，保证数据库复验记录可以被其他成员复查。

## 4. 个人收获

通过本次课程设计，我进一步理解了前端界面、后端接口和数据库结构之间的完整协作关系。页面能够显示并不代表功能已经完成，真正的验收还需要检查数据库持久化、权限边界、失败状态、刷新恢复、多窗口并发和构建结果。

本次工作也让我认识到，测试证据必须能够被其他成员重复理解。相比只写“测试通过”，保留操作步骤、预期结果、实际结果、截图和环境信息更有利于团队交接和答辩说明。

在数据库复验过程中，我掌握了通过 `information_schema` 检查表、字段、索引和外键的方法，并能够区分结构核验、业务验收、测试库升级和正式业务库迁移之间的差异。

## 5. 不足与改进建议

- 当前生产构建仍有较大的 JavaScript 分块，后续可以通过动态导入和路由级拆分降低首屏资源体积；
- 页面手工验收已覆盖核心流程，但第二账号、只读成员和归档项目等权限组合仍适合由接口自动化与团队联合验收继续补充；
- 数据库复验基于本机开发数据库，正式业务库的备份、恢复演练和迁移窗口仍应由成员 C 按流程完成；
- 后续可以将浏览器端核心流程进一步转化为端到端自动化测试，减少重复手工操作。
