# 跨模拟进度与复杂解锁说明

更新：2026-09-17。对应《隐藏路线跨模拟解锁问题报告》和《六线航海乙女游戏测试报告》。本轮完成代码与自动化回归，尚未对实际业务数据库执行迁移或修改项目 #17 的剧情配置。

## 1. 解决的问题与状态模型

旧实现把所有变量都当作单局状态，重开会恢复初始值；单一布尔开关也无法可靠表达多条路线的前置关系。现在区分：

| 数据 | 生命周期 |
| --- | --- |
| SESSION 变量 | 默认值；每次新模拟重新初始化，例如本局好感度 |
| PROFILE 变量 | 本人、同项目、同版本跨模拟保留，例如已获得的纪念物 |
| completedEndings | 到达 ENDING 节点时按 nodeKey 去重记录，重复通关不重复累计 |
| visitedNodes | 记录已进入的节点，包括起点，可作为跨模拟前置 |
| 步骤进度快照 | 保存 progressBefore / progressAfter，历史回放不被之后的清档或通关改写 |

PROFILE 效果在每次成功推进时立即保存，不是仅通关才保存。中途终止不撤销已提交进度；“必须打通某条线”应使用 ENDING 条件，不能用过早设置的标记替代。SESSION 和 PROFILE 均支持现有类型与效果运算。

进度以 (project_id, tester_id, version_key) 唯一隔离：version_key=0 为当前编辑版，正值为发布 ID。不同用户、项目、发布版本不互通。新发布不会自动复制旧版本进度。

## 2. 复杂解锁规则

选择现在可以附加 unlockRule。最终可用条件为“原有条件组成立 AND 高级解锁规则成立”；不配置高级规则时保持旧行为。

| 类型 | 含义与字段 |
| --- | --- |
| ALL | children 全部满足 |
| ANY | children 至少一个满足 |
| NOT | children 恰好一个，对它取反 |
| AT_LEAST | children 中至少 count 个不同条件满足 |
| ENDING | nodeKey 指定的结局已通关 |
| VISITED | nodeKey 指定节点已访问 |
| VARIABLE | variableKey、operator、value 比较当前状态（已覆盖最新 PROFILE 值） |

可嵌套组合。例如“路线 A 的好结局或普通结局 + 路线 B 通关 + 本局好感达到阈值”：
```json
{
  "type": "ALL",
  "children": [
    {"type": "ANY", "children": [
      {"type": "ENDING", "nodeKey": "a_good"},
      {"type": "ENDING", "nodeKey": "a_normal"}
    ]},
    {"type": "ENDING", "nodeKey": "b_good"},
    {"type": "VARIABLE", "variableKey": "affection", "operator": "GTE", "value": "80"}
  ]
}
```
以上 key 只是说明用占位符，必须替换为本项目真实定义。VARIABLE 沿用原有类型校验和操作符，布尔量不能做大小比较。无变量的项目也能单独配置结局规则。

限制：根节点计入最多 8 层、总计 128 个规则节点、每组最多 32 个子条件、JSON 最多 32768 字符。拒绝未知类型、无关字段、空组、错误引用及 AT_LEAST 中结构等价的重复条件；不会执行任意脚本。规则描述会在模拟页显示锁定原因，当前面向作者调试，不是隐藏剧透的玩家发行界面。

## 3. 六线航海项目的配置顺序

报告显示尼克尔单线 HAPPY ENDING 已设置 hidden_routes_unlocked=true。因此仅把这个变量改为 PROFILE，会把“单线提前解锁”永久保存，并不能实现“四条主线通关”。

1. C 先备份，在独立 MySQL 测试库升级并验证；不要直接覆盖现有业务库。
2. B/作者在当前编辑版找到两个隐藏入口（包括报告中的“跟随希尔法法进入雾海”）。
3. 在规则编辑器添加 ALL，下面分别选择四条主线的实际 ENDING 节点。若某条路线多个结局都算通关，用 ANY 包住该路线允许的结局，再作为 ALL 的一个子组。
4. 检查并移除已被替代的旧 hidden_routes_unlocked==true 基础条件；保留其他确实需要的本局条件。基础条件与高级规则是 AND，留下始终为 false 的 SESSION 开关仍会阻塞入口。
5. 旧的单线 SET 标记不再作为隐藏入口的唯一依据；按业务重新命名或清理效果。真正要跨局保存的收集物、事件标记才设置 PROFILE，并确认触发时机。
6. 四条线逐次通关并重开：前三条未满足时隐藏入口不可用；第四条完成后，同一用户同一版本重开可用。重复同一结局不能代替其他路线。需要额外条件的彩蛋，在 ALL 中继续增加 VARIABLE / VISITED 等条件。
7. 旧发布快照不可变；修改当前编辑版后重新发布，并在新版本重新验证。不会修改已有冻结内容。

本轮未猜测节点 key、未批量改写项目 #17；上述具体剧情配置需在实际数据上核对后进行。

## 4. 前端与接口

状态变量页面新增保存范围；选择规则弹窗新增递归规则编辑器；模拟页新增本人跨局进度、清档、编辑者测试预置、锁定原因和步骤快照。

以下接口均以 /api 为前缀，使用登录身份，不接受代替其他用户的 testerId：

| 方法与路径 | 约定 |
| --- | --- |
| GET /projects/{id}/player-progress | 项目成员读取本人进度；可选 releaseId 查询发布版 |
| POST /projects/{id}/player-progress/reset | 请求 expectedRevision、confirm:true；成员清空本人该版本进度 |
| PUT /projects/{id}/player-progress | OWNER/EDITOR 设置本人测试进度；请求 expectedRevision、confirm:true、values、completedEndings |

values 为 PROFILE 变量 key 到字符串值的映射，completedEndings 为结局 key 数组。预置是替换操作，未提供的 PROFILE 值回退初始值；访问记录仅保留选定结局。不会创建真实通关会话，也不增加通关覆盖统计。

清档/预置前必须结束本人该版本全部 RUNNING 模拟，项目不可归档；修订号冲突返回 409，必须刷新再确认。两者都保留历史会话与步骤。

变量请求/响应新增 persistenceScope（SESSION/PROFILE，缺省 SESSION）；选择规则请求/响应新增 unlockRule，传 null 可清除。模拟会话响应新增 progress 和 lockedChoices，步骤新增 progressBefore / progressAfter。

## 5. 兼容、并发与引用

不存在进度行时，从本人同版本已有 COMPLETED 会话推导结局记录；第一次写入后以存档为准。不会从旧会话猜测 PROFILE 值，也不补齐历史所有中间访问节点。主动清档会保留空进度行，防止旧通关记录重新导入。

推进时在既有项目锁及事务内读取最新跨局值，计算效果、写进度、写步骤并更新会话；失败整体回滚。同一请求的过期步骤不能重复加值；不同会话不会用旧 PROFILE 值覆盖最新值。

高级规则或当前编辑版进度引用的节点/变量稳定 key 受保护，不能任意重命名、删除或改变语义类型；展示标题可调整。需要重构时先移除规则引用并处理相关用户自己的测试进度，或建立新的稳定 key。发布快照仍受原有保护。

新发布和 JSON 导出使用 schemaVersion=2；读取兼容 1/2。旧数据缺少范围时按 SESSION；版本 1 导入不得夹带新特性。导入导出保留规则及变量范围，不携带任何玩家进度。按稳定 key 引用，避免数据库 ID 迁移导致规则失效。

新库顺序：修改选库名后的 schema.sql 副本 → schema-extension.sql → progression-extension.sql。已有 20 表库只执行最后一个增量，已有 21 表库只核验，不重复执行 ALTER。
