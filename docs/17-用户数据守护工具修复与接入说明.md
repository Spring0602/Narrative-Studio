# 用户数据守护工具修复与接入说明

日期：2026-10-13。基于 C 的 `tools/user-data-guard` 分支 `44256a8`，由 A 接手修复，不再要求 C 修改代码。

## 保留的改动

独立 Python 工具与 Windows 入口、白名单、只读检查、正常数量变化告警、本地配置和备份忽略规则、快照指纹校验均保留。不会自动运行此工具，也不会随应用启动连接数据库。

## 修复的问题

1. v2 项目 ID 映射会被后续内容表初始化清空；同名项目也不是唯一身份。新恢复流程不再猜测跨库映射，而要求同连接、同库 v3 快照及作品内容指纹一致，作品 ID 或内容变化即停止。
2. 用户/项目/会话/步骤关联不明时拒绝恢复。已有记录保留，非用户记录内容冲突直接停止；用户名迁移到不同 ID 不自动恢复权限。发布进度的版本归属也需核对。
3. 不再使用 INSERT IGNORE、REPLACE 或仅比较行数。缺失行使用普通 INSERT，保持外键与严格 SQL 模式，要求 InnoDB，提交后按具体记录核验。重复恢复已存在且一致的记录是成功的无操作。
4. 监控永远只报警；危险绕过选项返回明确失败。字段不兼容不再猜测必填默认值。
5. MySQL JSON 查询使用 raw 批量输出，避免 JSON 被再次转义。配置密码输入不回显；旧快照不覆盖，SQL 导出失败不报告 init 成功。

## 使用限制

- 只接入本地代码，不执行真实数据库操作。
- init 和 restore 前必须停写，不能与应用或 Navicat 写入并行。工具不负责停止其他写入进程。
- v1/v2 保险箱保留不动。只有健康数据仍在时，先归档旧保险箱，再停写创建 v3；数据已丢失时不得重建快照覆盖恢复来源。
- 作品内容正常编辑也会使指纹变化并阻止恢复。这是有意采用的保守策略，不能用手改指纹绕过；此时应另行制定完整恢复/迁移方案。
- 恢复提交后的验证失败会明确报告“事务已提交”，不能把错误结果当成已经自动回滚。
