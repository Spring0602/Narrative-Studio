## 1. C 本次要完成什么

把已有20表数据库升级到21表，让实体新增字段与实际表结构一致，并完成备份恢复、结构核验和业务验收。

不需要重建已有数据库，不需要 Docker，不需要修改原有节点或选项 ID。Excel导入功能复用已有表，不额外增加表。AI生成Excel暂缓，不在本次交接范围。

| 对象 | 要做的变更 | 用途 |
| --- | --- | --- |
| state_variable | 增加 persistence_scope VARCHAR(16)，非空，默认 SESSION | 区分单局变量和跨局变量 |
| story_choice | 增加 unlock_rule JSON，允许空 | 存储组合解锁条件 |
| playtest_step | 增加 progress_before、progress_after，均为可空 JSON | 保存每步前后的跨局进度快照 |
| player_progress | 新建表 | 保存本人、项目、版本隔离的跨模拟进度 |

player_progress 包含 id、project_id、tester_id、version_key、revision、progress_json 六列。唯一键为 (project_id,tester_id,version_key)，项目和用户外键采用级联删除。version_key=0 表示当前编辑版，正数表示发布版本ID，由应用校验其所属项目；不要额外建立一个无法容纳0值的发布版本外键。

旧变量默认保持 SESSION，不会自动成为跨局变量；旧步骤的新增快照列允许为空，迁移不猜测或回填历史状态。

## 3. 执行前检查与备份

1. 获取上述提交或更新的 main。若本地有未提交修改，先保留并协调，不使用强制重置。
2. 和 A/B 确认目标：MySQL地址/端口、数据库名、当前表结构、使用该库的后端实例和测试人员。不能只凭 Navicat 连接显示名判断。
3. 创建独立测试库，优先使用受控的现有库副本验证。不要将带真实数据的备份上传到GitHub或公开网盘。
4. 备份完整结构和数据（包括相关视图、触发器等现有对象，如有），记录备份文件位置、生成时间与恢复方法。
5. 把备份实际恢复到独立库，验证能恢复且关键表数据完整。若备份SQL含 CREATE DATABASE/USE 或全限定库名，先检查并在副本中改为测试库，不能直接执行仍指向业务库的备份。
6. 正式业务库迁移前暂停所有连接该库的后端写入、定时任务和人工编辑；页面上关闭一次模拟不等于全库停写。
7. 在 Navicat 新建查询窗口，显式选中目标库，并先执行：

```sql
SELECT DATABASE() AS selected_database,
       @@hostname AS server_host,
       @@port AS server_port,
       VERSION() AS mysql_version;
```

将结果与批准的目标逐项对照。selected_database 为 NULL、库名不符或服务器不符时立即停止。

备份、执行日志和截图只保存在团队受控位置。提交文档可记录文件标识，不记录数据库密码、连接凭据或个人敏感数据。

## 4. 判断当前结构，选择升级路径

先执行 verify-extension.sql。再查看 information_schema 中是否已有 player_progress 和本次四个新增列（verify-progression.sql 前半部分可用于只读结构检查）。

| 当前情况 | 操作 |
| --- | --- |
| 完整20表基线，未出现本次新表/新列 | 执行 progression-extension.sql 一次 |
| 已完整具备21表及所有新增列、索引、外键 | 不再执行ALTER，只做核验及业务测试 |
| 仅17表基线 | 先按数据库总说明完成 schema-extension.sql，再核验20表，然后执行本次增量 |
| 新列/新表仅出现一部分，或旧基线检查不通过 | 停止整份执行，将现有结构发给A/B确认后制定补齐方案 |
| 全新空库 | 在独立新库依次完成基线→旧扩展→本次扩展；不是现有业务库的操作路径 |

“总共21张表”不等于结构正确，必须核对预期表名、列类型、默认值、唯一索引和外键。

## 5. 在独立测试库执行迁移

1. 记录迁移前关键表数量：state_variable、story_choice、playtest_step、playtest_session、story_node；保存只读查询结果，作为迁移后比对基准。
2. 再次执行 SELECT DATABASE()，确认是独立测试库且写入已暂停。
3. 打开仓库中的 progression-extension.sql，检查内容与本指南四项变更一致。
4. 完整执行一次并保存执行日志。该文件不含 USE，不会自动替你选库。
5. 任意语句失败立即停止，不要继续手工尝试相似ALTER，也不要直接整份重跑。
6. 按下一节完成结构和数据核验。
7. 在同一测试库完成后端启动及业务验收。

MySQL DDL会自动提交。即使外层写了 BEGIN/ROLLBACK，也不能把这一组结构变更当作可整体回滚的事务。因此需要事前备份和恢复演练，而不是出错后依靠ROLLBACK。

## 6. 核验：应该看到什么

先执行 verify-extension.sql，再执行 verify-progression.sql。后者先看结构查询；缺表/缺列时停止，不继续运行依赖这些对象的数据查询。

| 检查项 | 预期 |
| --- | --- |
| verify-extension 的预期表数量 | 20；它只统计旧的20张已知表，即使升级后也仍然是20 |
| verify-extension 的扩展列结果 | 9行，逐项核对类型/可空/默认值 |
| verify-progression 的预期表数量 | 21 |
| 新增列查询 | 4行：persistence_scope、unlock_rule、progress_before、progress_after |
| player_progress 列查询 | 6列，与迁移SQL一致 |
| 索引 | PRIMARY，以及唯一索引 uk_progress_owner_version；列顺序为project_id、tester_id、version_key |
| 外键 | fk_progress_project→narrative_project.id；fk_progress_tester→sys_user.id；对照表定义核实ON DELETE CASCADE |
| invalid_scopes / invalid_progress / orphan_release_versions | 各为0 |
| duplicates 查询 | 不返回任何行 |
| 迁移前已有业务表的行数 | 在未恢复写入且未开始测试前，与迁移前一致 |

必要时运行 SHOW CREATE TABLE player_progress 查看完整DDL并与脚本对照。只读核验脚本只检查列和数据的部分结构特征，不证明业务规则正确。

初次迁移后、尚未启动应用或进行试玩时，player_progress 应是空表；原变量 persistence_scope 应为 SESSION。应用之后会按当前身份建立进度，不能用“表中已有记录”判断迁移失败。

## 7. 后端启动和业务验收

让 A 协助确认后端使用更新后的代码，并让 DB_URL、DB_USERNAME、DB_PASSWORD 明确指向刚核验的独立测试库。不要把数据库密码写入仓库配置或交接截图。

启动会执行只读结构检查：缺列、缺表或读取权限不足时会报错，不自动执行DDL。禁止通过关闭结构检查来掩盖迁移缺失。

建议使用独立测试项目、至少两个测试账户，逐项留证：

| 验收项目 | 操作与预期 |
| --- | --- |
| SESSION / PROFILE | 创建单局好感度和跨局标记，成功选择后重开；SESSION恢复初值，PROFILE保留 |
| 中途终止 | 成功步骤写入的PROFILE仍保留，但未到达ENDING不能记作通关 |
| 四条主线解锁 | 隐藏入口用ALL引用四个不同主线结局；前三条后不可用，第四条完成后同版本重开可用 |
| 重复通关 | 重复同一结局不会替代其他路线、不会累计成四条不同结局 |
| 直接请求绕过 | 锁定入口不能靠直接发送选择请求绕过后端条件 |
| 用户/版本隔离 | 另一用户、编辑版与发布版、不同发布版之间不能串进度 |
| 清档保护 | 本人该版本有RUNNING模拟时拒绝清档；全部结束后确认清档，历史会话保留且旧通关不重新导入 |
| 测试预置 | OWNER/EDITOR只能设置本人进度，TESTER不能预置；预置不增加真实通关覆盖统计 |
| 历史快照 | 后续通关或清档后，之前步骤的进度快照不变 |
| Excel导入 | 导入新项目/当前空图后节点和连线数量与预览一致；已有图不能被覆盖；错误文件不能产生半成品 |

## 8. 四线项目要特别注意：改表不等于改好剧情

报告中尼克尔单线结局已经把 hidden_routes_unlocked 设置为 true。因此**仅将这个变量改成PROFILE，会把提前解锁的错误保留下来**。

- 由 B/剧情作者核对真实结局节点，A协助规则；在两个隐藏入口配置 ALL，引用四条主线实际结局。不要猜节点key，也不要给所有用户统一写true。
- 一条路线允许多个结局时，用ANY组合该路线允许的结局，再放入四路线ALL。
- 检查是否仍留着过时的 hidden_routes_unlocked==true 基础条件。基础条件与高级规则是AND，旧SESSION标记为false仍会挡住入口。只移除已确认被替代的条件，不批量删除其他合法条件或效果。
- 收集物等确实需要跨局的变量才设为PROFILE，并确认效果触发时机。不要把所有变量批量改成PROFILE。
- 旧发布快照不修改；在当前编辑版确认规则后重新发布，新版本进度独立。
- 首次读取旧进度可由本人同版本已有COMPLETED会话推导结局，不能据此假设历史跨局变量或全部中间访问记录都会自动补齐。

C负责核验与留证，不需要直接用SQL重写剧情规则；具体配置见[复杂解锁说明](14-跨模拟进度与复杂解锁说明.md)。

## 9. 出错时怎样处理

| 问题 | 处理 |
| --- | --- |
| Duplicate column / Table already exists | 可能已执行过或部分成功；停止重跑，核对现有对象与脚本，交A/B确认 |
| 外键无法创建 | 核对引用表、ID类型、索引、引擎及现有结构；不要靠关闭外键检查绕过 |
| 后端仍提示缺少21表扩展 | 核对后端DB_URL与Navicat是否同库，以及应用账户是否有读取权限 |
| 结构核验通过但隐藏线仍不解锁 | 检查用户/版本、真实通关节点、基础条件与高级条件，不要直接改存档JSON蒙混通过 |
| 执行选错库、迁移部分失败或业务验收失败 | 暂停写入，保存日志与当前结构；联系A/B，不自行删表、删列或覆盖恢复 |

需要回退时，由团队确认目标库和恢复范围，使用已验证备份恢复，配套切回相容代码。迁移后若恢复过写入，新数据不能直接被旧备份覆盖；先保存增量并制定恢复方案。不要把手工DROP新表/列当作安全回退，它会丢失新的跨局记录。
