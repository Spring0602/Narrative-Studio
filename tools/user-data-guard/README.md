# 用户数据守护（user-data-guard）v2

> **一句话**：项目更新（换版本、重建表、换库名）经常会**把用户数据清空**——账号、成员关系、模拟测试记录、反馈全没了。这个工具提前把用户数据存进“保险箱”，每次更新后检测；确认是灾难后，再把用户数据搬回来，**故事内容一个字都不动**。
>
> **v2 改动**：按代码审计意见收紧了安全性——只认白名单、告警与灾难分开、搬运前核验身份与关联、默认不自动写库、凭据不进仓库。

发给你的是一个**完整独立的小工具**，不依赖项目代码，放在任意文件夹都能用。

---

## 0. 前提条件

- **Python 3.10+**（安装时记得勾选 *Add python.exe to PATH*）
- **本机有 MySQL**，并且你知道连它的账号密码
- **不需要安装任何第三方包**（只用 Python 标准库 + 本机 `mysql.exe` / `mysqldump.exe`）

---

## 1. 为什么需要它（我们真遇到过的问题）

换一版代码 / 重新执行建表脚本 / 把演示数据整库覆盖过去，结果**用户数据被清空**，登录时才发现在。

- 前端更新本身不会删数据，**真正会删数据的是“后端的数据库脚本 / 建表初始化 / 整库覆盖”**，所以这个工具盯的是**数据库**。
- 它只关心「用户数据 + 用户相关记录」，**剧情节点、选项、世界观、角色这些“作品内容”一律不碰**。

### 它管的 6 张表（默认）

| 表 | 是什么 |
|---|---|
| `sys_user` | 用户账号本体（含密码哈希） |
| `project_member` | 用户与项目的关系（谁是拥有者/测试员） |
| `playtest_session` | 用户跑的模拟测试会话 |
| `playtest_step` | 每一次模拟测试的步骤明细 |
| `test_feedback` | 用户提交的测试反馈 |
| `player_progress` | 用户的跨局进度 |

### 可选（默认不搬，加 `--include-optional` 才带上）

| 表 | 为什么不默认搬 |
|---|---|
| `project_save` | 用户创建的存档，里面**含项目内容快照**，搬它等于动了作品内容 |
| `account_action_token` | 找回密码的临时令牌，一般没价值 |

## 2. 怎么用（五步，都靠双击）

> 下面提到的文件名就是**本文件夹里的文件**，双击运行即可。所有 `.bat` 会自动找到你机器上的 Python。

### 第 1 步：填配置 —— 双击 `1-填配置.bat`

按提示回答 6 个问题（MySQL 地址、端口、用户名、密码、**要保护的数据库名**、项目文件夹可选）。
重点是 **MySQL 密码** 和 **要保护的数据库名**。

答案会写进 **`guard.config.local.json`**（本机真实配置，**不会被提交到 Git**）。
填完这一项后，**受保护库白名单 = 你填的那个库**——工具只碰它，不会去动别的数据库。

### 第 2 步：建立保险箱 —— 双击 `2-建立保险箱.bat`

把当前的用户数据存进“保险箱”：输出会把 6 张表的**行数和内容指纹**列出来。
> 以后用户数据有较大变化时，再双击一次刷新即可。

### 第 3 步：检查一次 —— 双击 `3-检查一次.bat`

只看一眼当前状态，不改任何数据。输出三种结论之一：

| 结论 | 含义 |
|---|---|
| ✅ OK | 用户数据完好 |
| 🟡 ALERT | 数量有变化（可能只是正常删了成员/清了测试数据）→ **只提示，不恢复** |
| 🔴 WIPED | 灾难级：库/用户表消失、账号被清零 → 需要人工确认后恢复 |

### 第 4 步：开始监控 —— 双击 `4-开始监控.bat`

窗口开着就会按间隔检查，**默认“只报警、不写库”**：

```
[00:33:03] 🔴 检测到灾难级变化（narrative_studio）：sys_user 被清零（23 → 0）
[00:33:03]    当前是「只报警」模式 —— 请人工确认后执行：python guard.py restore --yes
```

不想守了，直接关窗口（或 `Ctrl+C`）。
> 确实希望它自动搬回，可在命令后加 `--auto-restore`（仍然只作用于白名单内的库，且搬运前会做全部核验）。

### 第 5 步：人工恢复（确认是灾难后）—— 双击 `5-人工恢复.bat`

顺序是：**校验快照 → 核验身份与关联 → 备份目标库 → 写入 → 写后核验**。
写库前会问你一句，回车默认不写。只想看看会做什么，加 `--dry-run`。

## 3. 命令行用法（喜欢敲命令的看这里）

```bash
python guard.py init                      # 建/刷新保险箱
python guard.py check                     # 检测一次（0=OK 3=ALERT 2=WIPED）
python guard.py restore                   # 搬运（会先问一句；非交互需 --yes）
python guard.py restore --dry-run         # 只核验不写库
python guard.py watch                     # 常驻监控（默认只报警）
python guard.py status                    # 看保险箱与白名单各库状态
```

常用选项：

```bash
python guard.py restore --yes                    # 非交互确认（定时任务用）
python guard.py restore --on-conflict skip       # 跳过身份/关联冲突的记录，搬其余部分
python guard.py restore --allow-missing-tables   # 目标库缺表时跳过而不是中止（默认中止）
python guard.py watch --interval 5               # 每 5 秒检查一次
python guard.py watch --auto-restore             # 灾难时自动搬运（不推荐，默认关闭）
python guard.py check --include-optional         # 把存档表也一起保护
```

**白名单**：默认只保护配置里的 `target_db`。要同时保护多个库，在 `guard.config.local.json` 里写：

```json
"target_dbs": ["narrative_studio", "narrative_studio_v2"]
```

工具**不会**再去自动扫描“所有含 `sys_user` 的库”。

## 4. 它怎么判断“被清空”（判定规则 v2）

### 灾难级（🔴 WIPED，可恢复，需人工确认）

| 情况 |
|---|
| 目标库整个不见了 |
| 某张用户表在库里消失（被重建/改名） |
| `sys_user` 被清零（账号一个都不剩） |

### 告警级（🟡 ALERT，只提示，不恢复）

| 情况 |
|---|
| 其他用户表被清空（可能只是正常清理测试数据） |
| 任何表行数减少（**正常删成员、删测试记录也会命中**） |

> v1 的“账号少一个、其他表掉一半就自动整份恢复”已被移除——那会把正常删除误判成灾难、把旧记录又推回来。

---

## 5. 新版本改了表结构怎么办

1. **新增了列** —— 搬运时只写两边都有的列，新列走它自己的默认值；如果是「新增了 NOT NULL 且没有默认值」的列，会自动填安全占位值（数字 `0`、文本 `''`、时间 `NOW()`），并在日志里提示。
2. **新库名** —— 把新库名加进白名单，然后指定目标库：
   ```bash
   python guard.py restore --to-db narrative_studio_v2
   python guard.py restore --from-db 老库名 --to-db 新库名
   ```
3. **id 变了** —— 工具会按 **账号用户名**、**项目名** 自动把旧 id 对应到新 id；
   对应不上的（例如 id 已被另一个人占用、项目在新库里找不到）**默认直接中止**，
   不会把旧权限错绑到别人身上。

## 6. 安全设计（v2，逐条对应审计意见）

| # | 关注点 | 做法 |
|---|---|---|
| 1 | 不往无关库写数据 | **只认白名单** `target_dbs`（默认只有你自己填的那个库）；不再自动扫描其他库 |
| 2 | 不产生错绑数据 | 搬运前按 `sys_user.username` / `narrative_project.name` 重建 id 映射；id 被他人占用、子记录引用的项目/节点/会话在新库不存在 → **默认中止**（`--on-conflict abort`），确认无碍才用 `skip` |
| 3 | 密码/备份不进仓库 | 真实配置写在 `guard.config.local.json`（`.gitignore` 已忽略）；`vault/`、`logs/`、`*.sql` 全部忽略；仓库里只有不含密码的模板 `guard.config.json` |
| 4 | 正常删除不会被自动撤销 | 「数量变化」只报 🟡 告警；`watch` **默认只报警**；搬运默认**要人工确认**（非交互须 `--yes`） |
| 5 | 不会“没搬也报成功” | 写库前校验快照（文件存在、可解析、行数与指纹一致、非空）；目标库缺表**默认失败**；写库后逐表核验 before/after，不达标即报失败 |
| 附加 | 外键与回滚 | 默认**不关闭外键检查**（只有显式 `--disable-fk-checks` 才关）；整个过程在一个事务里；失败时出错 SQL 存到 `logs/last_restore_error.sql` |
| 附加 | 可追溯 | 写库前一律备份目标库到 `vault/backups/`；所有动作写 `logs/` |

## 7. 文件说明

```
用户数据守护-发给队友/
├─ 使用说明-先看这个.txt      30 秒上手（建议先看这个）
├─ 1-填配置.bat             双击 = 配置向导（写 guard.config.local.json）
├─ 2-建立保险箱.bat          双击 = 建/刷新保险箱
├─ 3-检查一次.bat            双击 = 只看状态，不改数据
├─ 4-开始监控.bat            双击 = 常驻监控（默认只报警）
├─ 5-人工恢复.bat            双击 = 核验 → 备份 → 搬运 → 写后核验
├─ setup-config.py          配置向导脚本（被 1-填配置.bat 调用）
├─ guard.py                 主程序（只用 Python 标准库）
├─ guard.config.json        模板配置（不含密码，可提交）
├─ guard.config.local.json  本机真实配置（含密码，不要外发；已 gitignore）
├─ .gitignore               忽略本地配置、保险箱、日志、备份 SQL
├─ vault/                   保险箱（第一次运行后自动生成）
│  ├─ vault.json            元数据：行数 + 内容指纹 + 代码版本 + 项目索引
│  ├─ user_data.json        数据本体（含密码哈希，自己留着别外发）
│  ├─ user_data.sql         同上的 SQL 版，方便人工恢复
│  └─ backups/              每次搬运前对目标库的完整备份
└─ logs/                    运行日志
```

**注意**：`vault/` 里存着用户数据快照（含密码哈希），`guard.config.local.json` 里有数据库密码，**都不要外发、不要提交**（`.gitignore` 已经帮你挡住）。
